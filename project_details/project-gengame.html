Core Conflict

A multiplayer arena prototype where players describe new mechanics, agents write and test them, and the server combines them into a shared match. The players are cows.

Player-made mechanics

Players request features from the lobby. A generation pipeline writes and tests the code, then a patch system combines the selected features before the match starts.

  • Every generated feature has to pass pytest before it's allowed in — fail, and the agent enters a fix loop.
  • A decentralized patch system merges each player's features, with the LLM resolving genuine code conflicts.

Feature generation

From a request to a mechanic

  • Describe it in English

    Type what you want — a new ability, a balance tweak — and the agent reads the actual game code and writes Python that plugs straight into it.

  • Test and revise

    Generated code runs through pytest, with a repair loop for failing tests.

  • Combine player features

    On game start the server gathers each player's chosen patches and merges them — caching, deterministic rules, and the LLM for real conflicts — into a shared match build.

Prototype scope

The experiment brings code generation into the game lobby: player requests become tested patches before a match starts. The generated mechanics and patch-merging workflow remain prototype features.

The evolution cycle

How a patch is born

01

Request

A player describes the mechanic they want, in plain English, from the lobby.

02

Build & test

A chain of specialized agents — planner, coder, tester — writes the Python and runs it through pytest, fixing until it passes.

03

Merge

At game start the server collects every player's patches and merges them, calling the LLM only for the conflicts it can't resolve on its own.

04

Hot-reload

The unified build syncs to every client and loads in — one match, everyone's ideas, running live.
