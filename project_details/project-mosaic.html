Robot-local control

Central visibility, local responsibility

The operator UI sends high-level commands through one supervisor bridge. It never publishes motor commands directly: each namespaced robot agent decides how to execute and when to stop.

  • Path following, manual drive, pose freshness, and cmd_vel remain on the robot.
  • Normalized Mosaic topics isolate the operator tools from vendor-specific ROSbot details.

System ownership

Robot, bridge, operator

Robot agent

One ROS 2 agent per robot consumes local sensors and OptiTrack pose, executes manual or autonomous movement, publishes normalized status, and owns the only motor-command publisher.

Supervisor bridge

The bridge translates UI UDP commands into high-level ROS actions, aggregates each robot's state, and preserves the flattened UDP payload expected by the external Gama visualizer.

Shared contract

A fleet configuration, public ROS interfaces, launch packages, and parallel deployment scripts keep namespaces, endpoints, device roles, and startup behavior consistent across machines.

The supervisor can disappear without becoming the robot

The ROS 2-first design removes the legacy centralized controller from the intended runtime and keeps stopping responsibility at the edge. Physical validation still depends on the real robots, generated ROS interfaces, OptiTrack, and the lab network; fleet membership also remains configuration-driven rather than dynamic.
